# 전체 개발 계획

## 문서 목적

현재 기획 문서를 실제 개발 일정과 분업 구조로 변환한다.  
이 문서는 8주 기준의 실행 계획이며, 실제 프로젝트 기간이 더 짧더라도 우선순위와 컷 기준은 그대로 유지한다.

## 프로젝트 목표

- 짧게 플레이해도 전투 손맛이 살아 있는 협동 로그라이트 데모를 만든다
- 콘텐츠 양보다 검 전투, 보상 3택, 보스전, 협동 부활 경험의 완성도를 우선한다
- MVP 기준 최종 목표는 `온라인 2인 협동 데모 완성`이다

## 성공 기준

- 검 1종 기준 전투 루프가 단독 플레이에서도 재미를 준다
- 온라인 2인이 한 판을 시작부터 종료까지 큰 문제 없이 완료할 수 있다
- 일반 적 3종, 엘리트 1종, 보스 1종이 최소한의 역할 차이를 보여준다
- 유물 10종과 상점 1종으로 보상 선택 재미가 느껴진다
- 결과 저장과 기본 진행 저장이 동작한다
- 도트 아트가 아직 정식급이 아니더라도 화면 톤과 판독성이 통일되어 있다

## 팀 구성 전제

- 백엔드/인프라 2명
- 클라이언트 3명
- AI 1명
- 백엔드 2명 모두 인프라와 백엔드 작업이 가능하므로, 고정 역할 분리보다 단계별 주담당 전환이 효율적이다
- 클라이언트 인력 중 최소 1명은 도트 작업 비중이 크므로, 실제 순수 기능 개발 여력은 `클라이언트 2~2.5명` 수준으로 본다

## 기술 스택 전제

- 클라이언트 엔진은 `Unity`로 확정한다
- 탑다운 전투 프레임워크는 `TopDown Engine` 사용을 전제로 한다
- 멀티플레이 목표는 `로컬 멀티`가 아니라 `네트워크 기반 온라인 코옵`이다
- TopDown Engine은 전투, 캐릭터, 카메라, AI, UI 같은 기본 게임 구조를 빠르게 확보하는 용도로 활용한다
- 온라인 코옵 기본 스택은 `Netcode for GameObjects (NGO) + Unity Transport + Relay + Multiplayer Services SDK`를 1차안으로 사용한다
- 접속 방식은 `초대코드/참여코드 기반 온라인 코옵`을 기준으로 하고, 호스트가 세션을 만들고 코드를 공유하면 참가자가 코드 입력으로 접속하는 흐름을 사용한다
- `Lobby`는 당장 필수로 보지 않고, MVP에서는 `Sessions/Relay + 초대코드`만으로 먼저 완성한다
- 온라인 코옵은 에셋 기본 기능에 기대지 않고, 우리 게임 룰에 맞는 네트워크 동기화와 세션 로직을 NGO 위에 별도로 구현한다는 전제로 계획한다

## 핵심 전략

- 처음부터 4인 완성형 로그라이트를 만들지 않는다
- 1챕터 전체보다 `전투 코어 + 코옵 골격 병렬 검증 -> 2인 협동 vertical slice -> 콘텐츠 확장` 순서로 간다
- 실시간 전투 서버는 만들지 않고, 호스트 기반 세션 + 서비스성 백엔드로 분리한다
- 전투 감각과 네트워크 안정성이 확인되기 전에는 메타 성장과 랭킹을 키우지 않는다
- 도트 아트는 초반 2주 동안 스타일 가이드를 먼저 고정하고, 그 전에는 임시 에셋으로 개발 속도를 유지한다
- TopDown Engine의 기본 구조를 최대한 활용하되, 에셋 원본을 직접 뜯어고치기보다 `우리 코드에서 상속/조합으로 확장`하는 방향을 우선한다

## 범위 고정

### MVP 포함

- 검 1종
- 기본 공격 3타, 대시, 패링, 다운/부활
- 일반 적 3종
- 엘리트 적 1종
- 보스 1종, 2페이즈
- 큰방 4개, 상점방 1개, 보스방 1개
- 이벤트방 0~1종
- 유물 10종
- 상점 기본 기능
- 결과 화면
- 게스트 또는 간단 로그인
- 유저 진행 저장
- 런 결과 저장
- 온라인 2인 협동 안정화

### MVP 제외

- 4인 안정화
- 자동 매칭
- 재접속 복구
- 호스트 마이그레이션
- 여러 챕터 동시 제작
- 무기 2종 이상 확정 구현
- 복잡한 스킬 트리
- 정교한 관리자 페이지
- AI 제작 도구의 공용 서버 고도화

| 데이터 방식 | 유물, 적, 상점 수치를 어떤 데이터 포맷으로 관리할지 확정 | 클라이언트 + 백엔드 |
| 배포 방식 | API, DB, 로그 수집, 빌드 배포 흐름 확정 | 백엔드/인프라 |

| 네트워크 브리지 전략 | TopDown Engine 캐릭터/능력 시스템과 코옵 동기화를 어떻게 연결할지 확정 | 클라이언트 리드 + 백엔드 |
| 스토리 동기화 기준 | 파티원 중 가장 스토리가 덜 진행된 플레이어 기준으로 동기화 | 클라이언트 리드 + 백엔드 |

## 권장 구현 원칙

### 게임플레이

- 전투 판정과 방 진행은 호스트 기준으로 처리한다
- 클라이언트는 입력과 표현을 담당하되, 핵심 진행 상태는 호스트가 결정한다
- 랜덤 보상, 적 스폰, 방 완료, 보스 페이즈 전환도 호스트 기준으로 통일한다
- 데이터는 코드 하드코딩보다 테이블 중심으로 관리한다

### 온라인 코옵 스택 원칙

- 게임 상태 동기화 기본 라이브러리는 `NGO`를 사용한다
- 전송 계층은 `Unity Transport`를 사용한다
- 초대코드 기반 세션 생성/입장은 `Relay + Multiplayer Services SDK`를 사용한다
- MVP에서는 세션 목록 탐색이나 자동 매칭보다 `호스트 생성 -> 코드 발급 -> 코드 입력 참가` 흐름을 우선한다
- 우리 백엔드는 실시간 룸 생성, 초대코드 발급, 연결 중계 역할을 직접 맡지 않는다
- 게임 저장, 진행, 결과 기록은 우리 백엔드가 맡고, 실시간 접속 흐름은 Unity 멀티플레이 서비스가 맡는 구조로 분리한다
- `Lobby`는 필요성이 확인되기 전까지 후순위로 둔다

### TopDown Engine 사용 원칙

- TopDown Engine 원본 폴더는 직접 수정하지 않는 것을 기본 원칙으로 한다
- 우리 게임 코드는 별도 폴더와 별도 네임스페이스에 두고, 필요한 경우 상속과 조합으로 확장한다
- 에셋 데모 씬은 기능 검증과 레퍼런스 확인용으로만 쓰고, 실제 게임 씬은 우리 구조로 다시 만든다
- 먼저 가져다 쓸 후보는 캐릭터 능력, 카메라, 피드백, 무기/투사체, AI 기본 구조, 룸/매니저 계열이다
- 나중에 직접 커스터마이즈할 후보는 보상 3택, 런 진행, 메타 성장, 온라인 코옵 상태 동기화, 우리 보스 룰이다
- TDE의 장점을 살리기 위해 초반부터 엔진 구조에 맞춰 설계하고, 에셋 구조와 충돌하는 독자 시스템을 섣불리 크게 만들지 않는다
- 멀티플레이 구조는 로컬 멀티를 목표로 하지 않고, 처음부터 온라인 세션 기준으로 설계한다

### 백엔드

- 게임 런타임 필수 의존성은 최소화한다
- 로그인, 저장, 랭킹 같은 서비스 기능만 맡는다
- 랭킹은 데모용 기능으로 취급하고, 치팅 방어를 과하게 설계하지 않는다
- 백엔드 2명은 API와 인프라를 나누되, 단계별로 주담당을 바꿔 병렬 처리한다

### 아트

- 초반에는 회색 박스와 임시 에셋으로 플레이 검증을 우선한다
- 도트 리소스는 캐릭터, 적, 이펙트, UI를 모두 동시에 만들지 않고 전투 가독성에 직접 영향 주는 것부터 만든다
- 몸체 애니메이션보다 무기 이펙트, 피격, 전조 이펙트를 먼저 살린다

### AI 활용

- AI 담당은 게임 플레이 로직의 핵심 담당자가 아니라 제작 생산성 보조 역할로 둔다
- 적 콘셉트 시안, 배경 레퍼런스, 아이콘, 로고, 초상, 프롬프트 자산화에 집중한다
- ComfyUI 공용 서버 구축은 데모 크리티컬 패스에서 제외한다

## 개발 단계

### 0단계: 프리프로덕션

기간:
- 1주

목표:
- 범위를 잠그고, 개발 기반을 깐다

산출물:
- 엔진, 네트워크, 저장 구조 확정
- Unity 프로젝트 생성 및 기본 패키지 정리
- TopDown Engine import 및 데모 씬 검증
- `NGO`, `Unity Transport`, `Relay`, `Multiplayer Services SDK`, `Multiplayer Play Mode` 설치 및 버전 고정
- 저장소 구조 확정
- 브랜치 전략, 코드 스타일, 이슈 관리 규칙 합의
- 전투 파라미터 시트 초안
- 유물 데이터 시트 초안
- 아트 스타일 보드 1차
- TDE 확장 포인트 목록 정리
- 온라인 코옵 위험 구간 목록 정리
- 호스트 생성/참여코드 발급/코드 입력 참가 흐름 설계

완료 기준:
- 팀원 모두가 같은 MVP 정의를 공유한다
- 제외 항목이 문서로 명시된다
- 클라이언트와 백엔드가 동시에 착수 가능하다
- TopDown Engine으로 무엇을 바로 쓰고 무엇을 직접 만들지 합의됐다
- NGO와 Unity 서비스의 역할 경계가 합의됐다

### 1단계: 전투 코어 프로토타입

기간:
- 1주

목표:
- 검 전투 손맛과 코옵 기반을 동시에 검증한다

구현 범위:
- 이동
- 검 3타
- 대시
- 패링
- 피격
- 다운 또는 사망 처리
- 카메라
- 임시 이펙트
- TDE 기본 Character/Ability 조합 검증
- MMFeedbacks 기반 타격감 초안
- `NetworkManager`, `NetworkObject` 기반 플레이어 프리팹 1차 구성
- `Relay + NGO` 기준 호스트 생성/참여코드 입장 최소 프로토타입
- 2인 더미 캐릭터 이동 동기화 테스트

산출물:
- 회색 박스 전투 테스트 맵
- 1인 기준 반복 전투 가능 빌드
- 패링 성공 피드백 초안
- 2인 접속 및 이동 동기화 테스트 빌드
- TDE를 기준으로 한 플레이어 프리팹 1차 버전
- 참여코드 생성/입장 확인 가능한 네트워크 테스트 씬

완료 기준:
- 5분 이상 전투 테스트가 가능하다
- 조작 답답함이 심하지 않다
- 검 1타, 2타, 3타 차이가 체감된다
- 2인 접속, 위치 동기화, 세션 종료 흐름이 최소한 동작한다
- TopDown Engine 구조가 전투 코어 구현에 실질적으로 도움이 된다는 게 확인된다
- 참여코드 입력만으로 2인 접속이 가능하다

### 2단계: 코옵 베이스라인

기간:
- 1주

목표:
- 전투 핵심 액션을 2인 기준으로 깨지지 않게 만든다

구현 범위:
- 플레이어 위치/행동 동기화 안정화
- 공격, 피격, 적 타겟 반응 동기화
- 다운/부활 기본 규칙 동기화
- 호스트 기준 진행 상태 관리 초안
- 세션 입장/퇴장 예외 흐름 정리
- `NetworkVariable`, RPC 사용 기준 초안 정리
- TDE Character 상태와 네트워크 상태 동기화 규칙 초안
- TDE 캐릭터/어빌리티 내부 상태 흐름을 분석해 온라인 코옵 동기화 포인트를 정리

산출물:
- 2인 전투 테스트 빌드
- 같은 적을 상대로 기본 전투 테스트 가능
- 상태 동기화 기준 문서 초안
- NGO 동기화 규칙 초안

완료 기준:
- 2인이 같은 전투 상황을 거의 같은 상태로 본다
- 공격, 피격, 다운 처리에서 치명적 불일치가 자주 발생하지 않는다
- TDE 능력 체계와 코옵 동기화 연결 방식이 팀 내에서 합의된다
- 호스트 종료, 참가 취소, 코드 오류 같은 기본 예외 흐름이 확인된다

### 3단계: 2인 협동 vertical slice

기간:
- 1주

목표:
- 한 판의 뼈대를 2인 협동 기준으로 완성한다

구현 범위:
- 일반 적 3종
- 엘리트 1종
- 방 클리어 규칙
- 보상 3택
- 상점 기본 기능
- 큰방/작은방 흐름 검증
- 방 클리어와 보상 선택 동기화
- 호스트 기준 룸 진행 규칙 확정
- 시작 화면에서 `방 생성/코드 표시/코드 입력 입장` UX 최소 버전 구현

산출물:
- 로비 또는 시작 화면에서 한 판 진입 가능
- 큰방 1세트 클리어 후 보상 획득 가능
- 상점에서 구매 가능
- 2인 기준 `전투 -> 보상 -> 상점 -> 전투` 진행 가능
- 초대코드 기반 입장 UX 확인 가능

완료 기준:
- 2인 기준 `전투 -> 보상 -> 상점 -> 전투` 루프가 이어진다
- 유물이 플레이 감각에 차이를 만든다
- TopDown Engine 위에 올린 우리 게임 규칙이 에셋 구조와 심하게 충돌하지 않는다
- 플레이어가 개발자 도움 없이 초대코드로 방 생성/입장을 수행할 수 있다

### 4단계: 보스와 런 종료 흐름

기간:
- 1주

목표:
- 데모에서 보여줄 한 판의 끝을 만든다

구현 범위:

- 결과 화면
- 런 종료 보상 계산

산출물:
- 2인 기준 1챕터 데모 완주 가능
- 결과 화면과 보상 지급 확인 가능

완료 기준:
- 보스전이 일반 적전과 구분되는 패턴 경험을 준다
- 런 종료가 저장 가능한 형태의 데이터로 정리된다

### 5단계: 콘텐츠 및 연출 보강

- 1주

## 주간 운영 방식

- 주 1회 전체 플레이 테스트를 고정한다
- 플레이 테스트 후 기능 추가보다 컷 결정을 먼저 한다
- 모든 주차 종료 시 `다음 주에 절대 안 미룰 것` 3개만 남긴다
- 네트워크, 보스, 아트는 각각 별도 체크리스트로 관리한다

## 마일스톤별 체크포인트

### M1: 전투 감각 확인

- 검 3타 차별화가 느껴지는가
- 대시와 패링이 쓸 이유가 있는가
- 피격/타격 피드백이 눈에 보이는가
- 2인 접속과 이동 동기화가 가능한가
- 참여코드 생성과 코드 입력 접속이 가능한가

### M2: 한 판 구조 확인

- 2인 기준 10분 내외 플레이가 가능한가
- 보상 3택이 선택 고민을 만드는가
- 상점이 회복과 빌드 선택의 갈림길 역할을 하는가

### M3: 협동 안정성 확인

- 2인이 같은 방 상태를 공유하는가
- 부활, 전멸, 보상 선택이 어긋나지 않는가
- 진행 불가 버그가 허용 수준 이하인가

### M4: 데모 품질 확인

- UI가 최소한의 설명만으로 이해되는가
- 도트 아트와 이펙트가 판독성을 해치지 않는가
- 발표 시나리오 기준 1회 이상 무리 없이 완주 가능한가

## 주요 리스크와 대응

### 1. 범위 팽창

위험:
- 무기 추가, 챕터 추가, 4인 안정화 욕심이 일정 전체를 무너뜨릴 수 있다

대응:
- 2인 데모를 넘는 기능은 모두 버퍼 주간 이후로 미룬다

### 2. 네트워크 불안정

위험:
- 호스트/클라이언트 상태 불일치가 생기면 콘텐츠를 늘려도 의미가 없다

대응:
- 1단계부터 이동 동기화를 붙이고, 2단계에서 전투 동기화를 먼저 검증한다
- 콘텐츠 추가보다 동기화 안정화를 우선하며, 불안정하면 적 수와 방 수를 줄여서라도 코옵 루프를 먼저 살린다

### 3. Unity 서비스 의존성

위험:
- NGO, Relay, Sessions 연동이 꼬이면 접속은 되는데 실제 플레이 검증이 늦어질 수 있다

대응:
- 0단계에서 서비스 계정, 환경 변수, 패키지 버전을 먼저 고정한다
- 1단계에는 게임플레이보다 먼저 `호스트 생성 -> 코드 발급 -> 코드 입력 입장`을 확인한다
- Lobby는 빼고 최소 구성인 NGO + Transport + Relay + Sessions부터 붙인다

### 4. 에셋 의존 구조 충돌

위험:
- TopDown Engine 구조와 우리 게임 구조가 어긋나면, 초반 속도는 빨라도 후반 수정 비용이 커질 수 있다

대응:
- 원본 수정 대신 확장 위주로 간다
- 1주차 안에 캐릭터, 능력, AI, 매니저, UI 중 무엇을 쓸지/버릴지 명확히 나눈다
- 에셋 기능을 억지로 끼워 맞추는 것보다 필요한 부분만 취사선택한다

### 5. 도트 작업 병목

위험:
- 클라이언트의 아트/UI 담당 1명이 도트 작업과 화면 작업을 동시에 크게 가져가면 후반에 병목이 생긴다

대응:
- 초반에는 임시 에셋 우선
- 전투 가독성에 필요한 에셋부터 순차 제작
- 홍보용 아트와 게임 내 에셋을 분리 관리

### 6. 메타 성장 과설계

위험:
- 기억 시스템, 각인, 무기 해금이 한꺼번에 들어가면 UI와 저장 구조가 무거워진다

대응:
- 데모에는 `기억 시스템 최소 버전 1개`만 넣고, 나머지는 확장 항목으로 둔다

### 7. 백엔드 과투자

위험:
- 서비스 구조를 너무 크게 잡으면 정작 게임 데모 완성도가 떨어진다

대응:
- 로그인, 저장, 결과 기록 외 기능은 후순위
- 관리자 페이지는 필요 시 간단한 내부 도구 수준으로 제한

## 최종 정리

이 프로젝트는 `전투 손맛이 좋은 2인 협동 로그라이트 데모`를 만드는 방향으로 움직여야 한다.  
클라이언트 3명 중 1명이 도트 작업을 병행하는 구조에서는, 기능과 아트를 동시에 크게 벌리면 일정이 무너진다.  
따라서 초반 3주는 전투와 코옵 기반을 병렬로 올리고, 중반 3주는 협동 vertical slice와 콘텐츠를 붙이며, 마지막 2주는 저장 연동과 안정화에 집중한다.
