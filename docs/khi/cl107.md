## 🔥 핵심 발견 (plan 에 없던 것)

### 1. AttackStepData 가 SO 가 아닌 `[Serializable]` class — *결론은 동일하지만 근거 정정*

cl107_plan.md 결정 #5 의 가정 (SO 가능성) 과 다르게 `WeaponData.Steps[]` 배열 항목. *in-place 변경 금지* 결론은 동일하되 근거 정정. 미래 후속 CL 에서 동일 가정 시 [`WeaponData.cs:83-111`](../../client/LostMemory/Assets/_Project/Scripts/Runtime/Data/WeaponData.cs#L83) 참조.

### 2. AttackSpeed 치환 위치 누락 — `if (step.startupDuration > 0f)` 비교

cl107_plan.md 가정 4 곳에 L180 비교가 빠져있었음. local 변수 치환 시 *호출* 만 신경쓰고 *비교* 를 놓치기 쉬운 패턴. 후속 CL 에서 같은 패턴 (다른 stat 의 in-place 가능 SO data) 시 grep + 수동 검증 권장.

### 3. PlayerRelicInventory 가 어디에도 부착 안 된 상태

CL-106 / CL-107 까지 `PlayerRelicInventory` 는 *코드만 정의* 됐고 어떤 Scene/Prefab 에도 부착 안 됨 (GUID grep 0 결과). cl107_plan.md Step 8 의 *implicit 가정* 과 다름. 본 CL 검증 중 `RelicEffectApplier.Inventory` 슬롯에 드래그할 컴포넌트 인스턴스가 *없어서* 발견. `TestKhi_MinimalCharacter2D` 에 임시 부착으로 해결 — CL-110 의 RewardController 가 자체 GameObject 로 분리되면 옮길 수 있음.

### 4. EffectType 직렬화 누락 패턴 (분쇄의팔찌 + 붉은송곳니)

CL-106 Wave A 의 *큰회복약 누락* 과 동일 패턴이지만 *반대 방향* — Wave A 는 *4 필드 모두* 직렬화 안 됨, 본 케이스는 *Magnitude / Duration / Threshold 만 들어가고 EffectType 드롭다운만 default(None)*. Inspector 에서 숫자 칸은 직접 입력하면서 dirty 발생, EffectType 드롭다운은 *클릭 안 하면 변경 안 됨*. 검증 단계의 일부 effect 가 발화 안 하는 형태로 노출되어 *현상* 으로 발견하기 어려움.

**진단법**: `[StatModifier]` Add 로그가 *유물 획득 로그 옆에 없으면* 해당 asset 의 EffectType 의심 → `Read RelicData_*.asset` 으로 `_effectType` 값 확인.

### 5. EnemyKilledByPlayer 의 false-positive 위험 (검증 결과 무사)

cl107_plan.md 위험 #4 가정: "다른 시스템이 DOT 등으로 동시에 죽이는 경우 false-positive 가능". 본 검증에서는 *Health.Damage → Health.Kill 동기 호출 후 그대로 CurrentHealth = 0 유지* → 우리 체크 시점 (`hit.CurrentHealth <= 0f`) 에 정확히 0 으로 평가. 단순 검 데미지 시나리오에선 이슈 없음. DOT / 환경 데미지 / 다른 hitbox 가 동시 처치 가능한 상황에선 추후 검증 필요.

### 6. 한 swing 안에 다중 처치 시 AddTimed N 회 누적

붉은송곳니 검증에서 한 swing 의 active duration 동안 4 마리 동시 처치 → `AddTimed × 4` → AttackSpeed = `1 + 4×0.12 = 1.480` (48% 단축). 의도된 동작 — 합연산 정책상 stack 됨. 만약 *최대 1 회 제한* 이 필요하면 `RelicEffectApplier.HandleEnemyKilled` 에 `RemoveBySource(s.Source)` + AddTimed 패턴으로 변경 필요. 본 CL 은 cl107_plan.md 의 stack 정책 그대로 채택.
