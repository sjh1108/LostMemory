## 🔥 핵심 발견 (plan 에 없던 것)

### 1. RelicData.IsInstantUse 신규 추가 (사용자) → cl108_plan 의 회복약 정책 부분 무효

사용자가 cl108_plan.md 작성 후 RelicData 에 `_isInstantUse` 속성 추가 + PlayerRelicInventory.TryAdd 의 IsConsumable 분기 세분화 (보관 분기 신설). cl108_plan.md 의 Step 3 (`TryUseOrAdd`) / Step 4 (RewardPanelView) 가 모두 *불필요* 해짐. 옵션 C (보관만, 사용 UI 후속) 채택으로 정리.

### 2. CL-106 의 EffectType 직렬화 누락 패턴 *재발* — 반격의 표식 + 추적자의 망토

CL-107 의 *분쇄의팔찌 / 붉은송곳니 같은 패턴*. CL-106 작성 시점에 입력했지만:
- **반격의 표식**: Magnitude `0.8` (10배 큰 값, 입력 실수)
- **추적자의 망토**: EffectType `8 (MoveSpeedPercent)` (드롭다운 잘못 선택, 영구 이속이 됨)

*Inspector 직접 입력 작업의 시각적 검증 어려움* 패턴. 본 CL 검증 중 *시나리오 5 의 AddTimed 발화 안 함* + *보호막 부여량 너무 큼* 으로 노출 → 정정.

**진단 패턴**: `[StatModifier] Add ...` 로그가 *예상값과 다르거나* *유물 획득* 옆에 안 보이면 .asset 의 `_effectType` / `_magnitude` 값 확인.

### 3. KhiParryController permit race condition (간헐적) — **별 ticket 으로 분리**

CL-108 검증 중 *패링 1 회 후 공격/대시 영구 차단* 증상 발견. 진단 결과:
- `KhiParryController` state machine 자체는 정상 (logStateTransitions 로 추적, 모든 RestorePermits path 통과)
- 외부 시스템 (KhiHitStunController / KhiDownController 등) 이 *차단 set* 한 상태에서 패링 입력 → CachePermitsIfNeeded 가 *그 차단 값을 캐시* → RestorePermits 시 *외부 시스템이 이미 cleanup 한 변경을 다시 차단* → 영구 잠금
- 재현 빈도 = 간헐적 (CL-108 검증 시점에 dump 시도했으나 재현 안 됨)
- 본 CL 무관 (KhiParryController.cs 의 state machine 로직은 본 CL 에서 미수정. 디버그 ContextMenu 만 추가)

→ **별 ticket** 으로 분리: [cl108_followup_parry_race.md](cl108_followup_parry_race.md). 본 CL commit 에 *임시 디버그 ContextMenu 2 개 포함* 한 채 진행 (재진단 시 즉시 활용).

### 4. DungeonArchitect Build NRE (간헐적, CL 무관)

`DungeonArchitect.Dungeon.Build (L166) NullReferenceException` 가 CL-108 검증 중 자주 발생. 던전 빌드 실패로 적이 spawn 안 됨 → TestKhiDamageDummy / TestKhiDamageTrap 같은 *고정 더미* 로 우회 검증. CL-105 의 *DA Snap2D 시드 의존성* 와 같은 맥락 가능. CL-108 무관, 별 ticket 권장.

### 5. PlayerShield 보호막 흡수 (TryAbsorb) 미검증

본 CL 검증에서 `[PlayerShield] Grant + Expired` 까지는 통과 했지만 *데미지 흡수 (TryAbsorb)* 로그는 안 떴음. 보호막 부여 후 적의 다음 공격 (*트랩 데미지* 만 있고 적 부재) 이 트리거 안 됨. KhiParryDamageOnTouch 의 PlayerShield hook 코드는 정상 적용됨이 코드 review 로 검증. 적 spawn 정상 회복 후 후속 검증 권장.
