## 🔥 핵심 발견 (plan 에 없던 것)

### 1. Down 중 후속 hit 으로 GameObject 비활성 → tick 멈춤 패턴

**증상**: 타이머 기반 상태 전이가 *발화 자체* 가 안 일어남. `TickDown` 의 `[KhiDown] Down timer expired -> Defeated` 로그가 안 뜸.

**원인 chain**:
1. Player Down 진입 → 적이 OnTriggerStay2D 로 *Down 중 추가 hit* 부여
2. `Health.Damage` 가 HP 를 추가 차감 → 음수 도달
3. `Health.Damage` 끝에 `if (CurrentHealth <= 0) Kill()` → `gameObject.SetActive(false)`
4. GameObject 비활성 → `Update` 정지 → `TickDown` 멈춤 → Defeated 영원히 안 일어남

**진단 패턴**: 타이머 발화 자체가 안 일어나면 → **GameObject 비활성** 의심 → `OnDisable` 에 stack trace 로그 임시 추가하여 SetActive(false) 호출처 추적.

**Fix 패턴**: 비활성화 트리거 *진입점에서 차단* 이 가장 안전. 본 CL 은 `HandleHealthHit` 의 Down 분기에 HP floor 복원으로 `Health.Kill()` 발화 자체를 막음.

→ 향후 *상태 전이가 발화 안 됨* 류 미스터리 발생 시 *GameObject 활성 상태 + Update 가 도는지* 부터 검증 권장.

### 2. closure 캡처로 multiple instance source 식별

DungeonArchitect 가 같은 Module prefab 을 여러 번 spawn 시 여러 `RoomEntryRuntimeController` 인스턴스가 *같은 RoomId* 공유. RoomId 만으로 source 식별 시 *플레이어가 들어가지 않은 instance* 가 반환되는 케이스 발생.

→ 이벤트 구독 시 **closure 로 source 자체를 캡처** 하면 RoomId 매칭 우회. `Dictionary<source, handler>` 패턴으로 unsubscribe 도 안전.

### 3. cl110_progress.md *진행 중 문서* 의 가치

*막힌 지점* 섹션을 *증상 / 가설 / 진단 코드 / 다음 액션* 으로 구조화한 것이 fix 를 안내. 가설 1번이 맞았고, *다음 액션* 의 진단 로그를 그대로 따라가서 원인 좁힘.

→ 향후 막힌 지점이 생기면 *progress 문서 작성 → 가설 나열 → 진단 코드 추가 → 다음 액션 명시* 패턴 표준화 권장. 기록이 미래의 본인 (또는 동료) 에게 *재현 + fix* 의 안내가 됨.
