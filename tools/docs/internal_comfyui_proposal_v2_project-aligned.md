## 6. 추천 저장 구조

### 6.1 권장안

`GPU 데스크탑 로컬 임시 저장 -> S3 업로드 -> 웹은 S3 기준으로 조회`

### 6.2 권장 이유

- 내부 사용자 2~3명이 같은 결과를 중앙에서 보기 쉽다
- 목록/상세/다운로드 구현이 단순하다
- 데스크탑 로컬 경로 변화에 덜 민감하다
- 자산 백업과 관리가 수월하다

### 6.3 현재 프로젝트 반영 메모

- 위 저장 전략은 현재 문서 기준으로 유지한다.
- 다만 실제 업로드 구현은 아직 시작 전이다.
- 현재는 로컬 ComfyUI 기동과 API 확인 단계까지만 검증했다.

---

## 7. 워크플로우 및 메타데이터 저장 전략

### 7.1 기본 원칙

이미지 파일만 저장하지 않고, 생성에 사용된 워크플로우와 핵심 설정도 함께 저장한다.

### 7.2 저장 대상

- 결과 이미지 파일
- 워크플로우 스냅샷 JSON
- 생성 메타데이터
- 필요 시 prompt JSON
- prompt summary
- full prompt 또는 그에 준하는 복구 가능한 값

### 7.3 현재 반영 사항

- `workflow_snapshots`, `generations`, `generation_outputs`, `audit_logs`를 핵심 테이블로 유지
- `prompt_id`는 ComfyUI `/prompt` 응답과 연동하기 위해 generation 단위에서 관리하는 것이 필요
- 결과 상세 페이지는 workflow JSON 다운로드와 full prompt 접이식 노출을 기준으로 유지

## 17. 현재 컷 순서

1. 관리자 로그 페이지 고도화 제거
2. 상태 필터 제거
3. 내부 링크 공유 상세 정보 축소
4. workflow JSON 화면 내 노출 축소
5. 최근 오류 웹 화면 단순화

### 컷하면 안 되는 것

- ComfyUI 원본 UI 접속
- GPU 데스크탑 추론 연결
- S3 저장
- 결과 조회 페이지
- 기본 인증
- 간단 로그인
- 결과 상세 보기
- 이미지 다운로드
- 최근 생성물 목록
- 최소 로그 구조

---

## 18. 최종 정리

이 프로젝트의 핵심은 ComfyUI 자체를 다시 만드는 것이 아니라, ComfyUI 원본 UI를 유지한 채 내부 팀이 실제로 사용할 수 있는 접근 구조, 저장 구조, 조회 구조, 공유 구조를 붙여 내부 서비스로 만드는 것이다.

현재 기준으로는 문서 구조와 로컬 ComfyUI 검증이 먼저 정리되었고, 이제 체크포인트 적용, 첫 generation 검증, Spring Boot / S3 / SQLite 실제 구현으로 넘어가야 한다.
